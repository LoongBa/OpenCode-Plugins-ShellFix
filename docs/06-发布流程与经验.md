## 二、标准发布流程（SOP）

```
1. 改版本号          package.json + src/lib/state.ts（两处必须一致）
2. 写开发方案        docs/迭代开发记录/ShellFix-V{x.y.z}-开发方案.md
3. 实现 + 自检       LSP 零 error；npm pack --dry-run 校验包内容
4. 写审核报告        docs/迭代开发记录/ShellFix-V{x.y.z}-审核报告.md
5. 用户确认 → commit
6. 本地部署          .\deploy.ps1 → 校验 9/9 哈希 + PLUGIN_VERSION
7. 打 tag 并推送     git tag V{x.y.z} && git push origin V{x.y.z}
8. CI 自动发布       release（GitHub Release）+ publish-npm（npm publish）
9. 发布后验证        npm view / npm install
```

### 关键命令

```powershell
# 发布前：包内容自检（不产生文件）
npm pack --dry-run

# 提交并打 tag
git add -A
git commit -m "feat|fix|chore: v{x.y.z} <摘要>"
git push origin master
git tag V{x.y.z}
git push origin V{x.y.z}          # ← 这一条才触发 CI

# 观察 CI
gh run list --workflow=publish.yml --limit 3
gh run view <run-id> --log | Select-String "Run npm publish"

# 发布后验证
npm view @tkwf/opencode-shellfix version
npm view @tkwf/opencode-shellfix dist-tags
```

### 本地部署校验

```powershell
.\deploy.ps1
# 校验：9 个文件 SHA256 与 src/ 一致；部署版 PLUGIN_VERSION 等于新版本号
```

## 五、故障排查对照表

| 症状 | 根因 | 处理 |
|------|------|------|
| `E403 You do not have permission to publish` | token 对目标包/scope 无写权限；或账号不是该 org 成员 | 换 **org 成员账号**的 Automation token；用 `npm org ls <org>` 确认角色 |
| `E404 Not Found - PUT https://registry.npmjs.org/<pkg>` | 包名不存在且 token 无创建权限；或 scope 拼错 / 不属于该账号 | 确认 scope 归属；`npm access list packages "@<org>"` 看权限 |
| CI 日志有 `+ pkg@ver`，但 `npm view` / `npm install` 404 | **新包首发异步处理**，根 packument 尚未生效 | 等 4~5 分钟；用 `/<pkg>/<ver>` 与 tarball URL 判断是否已存在；**切勿重复发布** |
| `EPUBLISHCONFLICT` / `403 cannot publish over the previously published versions` | 同版本已发布，npm 不允许覆盖 | 升版本号（如 2.3.4 → 2.3.5）重发 |
| `npm whoami` → `E401` | 本地 token 过期/失效 | 重新 `npm login`，或改用 Automation token |
| CI `release` 绿、`publish-npm` 红 | secret 缺失/失效/无权限 | `gh run view <id> --log` 看 `publish-npm` 段错误码 |
| `opencode plugin <pkg>` 失败 | 包名解析或网络问题 | 退化为 `opencode.json` 手写 `"plugin": ["<pkg>"]` |

## 六、经验教训（2026-11-08 发布事故复盘）

### 6.1 npm 账号邮箱不可达 → 整条发布链断掉

**现象**：v2.3.0~v2.3.3 四次 CI 发布全部 `E403`；本地 token `E401`；无法登录 npm 重置。

**根因**：账号 `loongba` 的注册邮箱是 GitHub 隐私地址 `76543969+LoongBa@users.noreply.github.com`，**按设计不接收任何邮件** → 收不到 OTP → 无法登录 / 改邮箱 / 重签 token。

**教训**：
- npm 账号必须绑定**真实可收信**邮箱，不要用 GitHub noreply
- 开启 2FA 后立刻保存 **recovery codes**
- CI 用 **Classic Automation token**（不绑 IP、不过期、绕过 OTP），不要用登录态 token
- 关键账号信息（token、recovery codes）必须进密码管理器

### 6.2 非 scoped 包无法收录进 org

**现象**：在 `tkwf` org 的 Team → Packages 里输入 `opencode-shellfix`，返回 `forbidden`；按钮点了没反应。

**根因**（npm 官方答复）：
- 给团队授权**非 scoped 包**，要求「该包的**直接 owner** 同时是该 org 的成员」
- `opencode-shellfix` 的 owner 是 `loongba`，而 `loongba` 不在 `tkwf` → 403
- 那个输入框是**下拉选择**，只列 org 已有包；没有可选项 → 按钮永远灰

**教训**：
- npm **没有**包重命名/转移功能，非 scoped 包**搬不进** scope，只能新建发布
- 想走 org 路线，必须从一开始就发 **scoped 包**（`@org/name`）
- 事故应对：新建 `@tkwf/opencode-shellfix`，旧包保留并等待 deprecate

### 6.3 新包首发后的「假 404」窗口

**现象**：CI 明确输出 `+ @tkwf/opencode-shellfix@2.3.4`，但 `npm view` 和 `npm install` 连续 4~5 分钟报 404。

**真相**：
- npm 提示 `Your package is being processed and may take a few minutes to become available.`
- registry 里能查到占位版本 `0.0.0-stage` —— 处理中的标志
- 窗口内 `/pkg/2.3.4` 与 tarball 均 **200**，只有**根 packument** 404（npm CLI 走的正是它）
- 约 5 分钟后自动生效

**教训**：
- **npm 没有「手动创建包」这一步**，`publish` 即创建，不要去找「新建包」按钮
- 遇到 404 先用「单版本接口 + tarball」判断真假失败
- 千万不要在窗口期内重发同版本（会 `EPUBLISHCONFLICT`），也不要急着升版本号

### 6.4 版本号是发布的一部分，不是事后补的

- `package.json` 与 `state.ts` 的版本号必须同时改，否则运行时版本与 npm 版本不一致
- tag 必须与 `package.json` 版本严格对应，否则 CI 发布的版本和 tag 对不上
- 同版本不可重发 → 任何「重发」需求都要先升版本号

### 6.5 发布走 CI，不走本地

- 本地 `npm publish` 能过，但会绕过 tag ↔ 版本的一致性
- 统一走「打 tag → CI 发布」，GitHub Release 与 npm 同步产生
- 本地只做 `npm pack --dry-run` 校验
