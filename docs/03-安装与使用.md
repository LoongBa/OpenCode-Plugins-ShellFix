# 安装与使用指南

当前版本：**v2.3.4**

## 环境要求

| 依赖 | 版本要求 | 说明 |
|------|----------|------|
| OpenCode | ≥ 1.0（支持插件系统） | 内置 Bun 运行时，自动编译 .ts 文件 |
| 操作系统 | Windows（PowerShell 5.1+） | 解决的核心问题是 PowerShell 兼容性 |
| @opencode-ai/plugin | ≥ 1.17.13（选装） | 仅用于 TypeScript 类型检查，非运行必需 |

---

## 安装步骤

### 方式零：npm 一键安装（最快）

```bash
opencode plugin @tkwf/opencode-shellfix
```

或在 `~/.config/opencode/opencode.json` 中手动添加：

```json
{
  "plugin": ["@tkwf/opencode-shellfix"]
}
```

> **发布渠道迁移（v2.3.4）**：原包 `opencode-shellfix` 停在 2.2.12，后续版本统一发布到 `@tkwf/opencode-shellfix`。
> npm 包只含核心插件（`shell-fix.ts`）；需要 TUI 调度器（palette 入口 / 事件订阅 / 七命令体系）请按下面「步骤 1」手动部署。

### 步骤 1：放置插件文件

将 `src/shell-fix.ts` 复制到 OpenCode 的插件目录。

**全局安装（推荐）**——所有项目生效：

```bash
# 确认全局插件目录存在
mkdir -p ~/.config/opencode/plugins/

# 复制插件
cp shell-fix.ts ~/.config/opencode/plugins/
```

**TUI 调度器（可选，palette 入口 / 事件订阅 / 六命令体系需要）**：

```bash
# 1. 复制 TUI 插件到独立目录（tui.json 注册的加载路径）
mkdir -p ~/.config/opencode/tui-plugins/
cp shell-fix-tui.ts ~/.config/opencode/tui-plugins/
```

**2. 在 `~/.config/opencode/tui.json` 中注册：**

```json
{
  "$schema": "https://opencode.ai/config.json",
  "plugin": ["./tui-plugins/shell-fix-tui.ts"]
}
```

> ⚠️ 布局约束：`shell-fix-tui.ts` **必须**放在 `tui-plugins/`（而不是 `plugins/`），并通过 `tui.json` 注册；其内部以 `../plugins/lib/*` 引用公共库，因此 `~/.config/opencode/plugins/lib/` 下的 `state.ts` / `template-store.ts` / `auto-rules.ts` 必须一并存在。

**项目级安装**——仅当前项目生效：

```bash
# 在项目根目录创建 .opencode/plugins/
mkdir -p .opencode/plugins/

# 复制插件
cp shell-fix.ts .opencode/plugins/
```

**一键部署（推荐）**：仓库自带 `deploy.ps1`，自动完成核心插件 → `plugins/`、TUI 插件 → `tui-plugins/`、lib 公共库 → `plugins/lib/` 的全部复制，并校验/写入 `tui.json` 注册条目（旧版本自动备份到 `.bak/`）：

```powershell
.\deploy.ps1
```

### 步骤 2：重启 OpenCode

关闭当前 OpenCode 会话并重新启动。

### 步骤 3：验证安装

#### 验证 1：插件版本环境变量

在 OpenCode 中执行：

```powershell
echo $env:SHELLFIX_VERSION
```

预期输出：`2.3.4`

如果返回空或 undefined，说明插件未加载。

#### 验证 2：环境变量预注入

在 OpenCode 中执行：

```powershell
echo $env:CI
```

预期输出：`true`

如果返回空或 undefined，说明插件未加载。

#### 验证 3：export 自动转换

在 OpenCode 中让 Agent 执行：

```bash
export MY_TEST_VAR="HelloWorld"
echo $env:MY_TEST_VAR
```

预期输出：`HelloWorld`

测试没有 `export` 命令报错即成功。

#### 验证 4：中文编码

```powershell
Write-Output "你好，世界！测试中文不乱码"
```

预期输出：`你好，世界！测试中文不乱码`

#### 验证 5：多项 export

让 Agent 执行：

```bash
export DB_HOST=localhost DB_PORT=5432 DB_NAME=mydb
echo "$env:DB_HOST:$env:DB_PORT/$env:DB_NAME"
```

预期输出：`localhost:5432/mydb`

#### 验证 6：状态指令 `/shellfix`

让 Agent 执行 `/shellfix` 或 `#shellfix`，预期输出：

```
[ShellFix] v1.1.0
  ├ Status: Active
  ├ Export syntax: $env:KEY=VAL auto-convert
  ├ Encoding: UTF-8 forced prefix
  └ CI vars: 18 pre-injected
```

## FAQ

### Q：如何确认插件已加载？

三种方式：

1. **环境变量** — 执行 `echo $env:SHELLFIX_VERSION`，输出 `1.1.0`
2. **状态指令** — 让 Agent 执行 `/shellfix`，显示状态面板
3. **启动日志** — 检查 OpenCode 日志 `~/.local/share/opencode/log/opencode.log`，搜索 `[ShellFix]`

### Q：插件是否会影响非 Windows 系统？

不会。`shell.env` 钩子注入的 CI 环境变量是跨平台通用的（除 `DEBIAN_FRONTEND` 外，它在 Linux 上只是不生效，不会报错）。`tool.execute.before` 的编码前缀使用 PowerShell 语法，在 Linux/macOS 的 bash 工具中会自动报错：

```bash
$OutputEncoding=...  # bash 中报错：command not found
```

**因此建议仅在 Windows 环境中启用此插件。** 或者可以增强插件使其在非 Windows 平台静默退出：

```typescript
"tool.execute.before": async (input, output) => {
  if (process.platform !== "win32") return; // 非 Windows 跳过
  // ...
}
```

### Q：和现有插件冲突吗？

插件使用 `shell.env` 和 `tool.execute.before` 两个标准钩子。如果有其他插件也使用相同钩子，OpenCode 按加载顺序依次执行所有插件的同名钩子。多个插件可以通过 `output` 对象链式传递修改结果。

如果出现冲突，调整插件加载顺序或在 `opencode.json` 中明确指定顺序。

### Q：export 语法转换是否 100% 兼容 bash 语义？

不完全。见"局限性"章节。主要差异：

| Bash 语义 | 插件行为 | 差异 |
|-----------|----------|------|
| `export FOO=$BAR`（引用变量） | `$env:FOO="`$BAR"`（字面量） | `` `$BAR `` 在 PS 中是字面量而非变量引用 |
| `export FOO=$(cmd)`（命令替换） | 不支持 | 正则无法匹配 `$()` 和反引号 |
| 多行 export | 不支持 | `export FOO=bar \` + 换行 + `BAZ=qux` |

这些场景在 LLM 生成的命令中极少出现，实际影响有限。

### Q：$PROFILE 不加载了，自定义环境变量怎么办？

通过 `shell.env` 钩子手动注入。如果需要自定义环境变量，在 `shell-fix.ts` 的 `CI_ENV_VARS` 对象中添加即可：

```typescript
const CI_ENV_VARS: Record<string, string> = {
  // ...默认变量...
  MY_CUSTOM_KEY: "my_custom_value",
  ANOTHER_VAR: "another_value",
};
```

### Q：`/my` `/auto` 出现两条菜单，或手敲 `|my` 没反应？

两个坑（已修正）：

1. **菜单重复**：`opencode.jsonc` 的 `command.my/auto` 与 TUI 插件的 `slashName` 各注册一次。现统一为**插件 `config` 钩子自注册**（`shell-fix.ts` 钩子 0b，注册 `codemap-index` / `my` / `auto`），用户配置中不要再写 `command.my/auto`，TUI palette 项也不再带 `slashName`。
2. **手敲 `|my ?` 不生效**：`|my` / `/my` 的管道拦截位于 `tool.execute.before`，只覆盖 **Agent 调用 bash 工具**的场景；用户在输入框直接提交 `|my ...` 不经过任何钩子，会作为普通消息发给模型。正确入口是斜杠命令 `/my`（config 注册 → `command.execute.before` 本地处理）或 palette（`Ctrl+P`）。

### Q：CodeMap 日志报 `refresh_overlay failed` / `Workspace 'session' not found`？

v2.3.2 起自动路径**不再写 overlay**（编辑 `.cs` 不再触发 `refresh_overlay`），改由 Agent 侧 codemap MCP 维护，避免两个进程同写 `~/.codemap/store/overlays/session/overlay.wal` 导致 `IOException: being used by another process`。

历史成因（v2.3.1 及以前）：

1. workspace id 是全局常量 `session`，overlay 路径 `~/.codemap/store/overlays/<ws>/` **不带仓库维度** → 不同仓库、不同进程共用同一个 WAL
2. opencode 自带的 `mcp.codemap` 与 ShellFix 各自 spawn 的 `codemap-mcp.exe` 同时打开该 WAL → 写入方撞锁
3. `workspace.create` 失败被静默丢弃；刷新路径从不重新 ensure → 进程重启/空闲 5 分钟回收后必然 `NOT FOUND`
4. 可恢复正则 `not found` 误匹配 workspace 错误 → 白杀进程重启再失败

仍可用的显式路径：`/codemap-index`（重建 baseline + 创建 workspace + 刷新 overlay），撞锁会按 300ms / 1.2s / 3s 退避重试，失败给出中文可操作提示。

> 另一个历史坑：`index.refresh_overlay` 的 `file_paths` 必须用正斜杠（`INVALID_ARGUMENT ... forward slashes only`），现已统一 `replace(/\\/g, "/")`。

### Q：思考截断 / codemap 未建索引会有 toast 提示？如何关闭？

v2.3.1 新增「调试提示」通用通道（toast + 计数）：

- **思考截断**：`session.idle` 检测到末条回复无正文且思考断尾 → toast「思考截断」（红）+ 计数 `think-cut`
- **codemap 未建索引**：调用 `codemap_*` 工具报 `repo_path is required` 等 → toast「CodeMap 未建索引」（橙）+ 指引 + 计数 `codemap-no-index`

关闭：palette `shellfix.alerts` 或 `/shellfix alerts` 切换总开关 `alertToasts`（默认 ON）。**关闭后 toast 不弹，但计数仍累计**（`alertCounts` 持久化 `shellfix-state.json`，供 `/shellfix doctor` 排查）。同场景 5 分钟最多 1 条，防刷屏。

### Q：toast 颜色代表什么？为什么模板执行不再填输入框？

v2.3.2 起两侧（TUI 本地 / 服务端）toast 统一四色：

| 颜色 | variant | 语义 |
|------|---------|------|
| 蓝 | `info` | 中性信息（列表为空、无副作用提示） |
| 绿 | `success` | 操作成功（已保存 / 已删除 / 开关切换 / 已发送模板） |
| 橙 | `warning` | 缺失或受阻（不存在 / 参数无效 / 内容为空 / 稍后重试） |
| 红 | `error` | 失败（渲染失败 / 保存失败 / 异常） |

`/my <name>` 与 palette「模板执行」改为**直接发送消息 + 绿色 toast「已发送」**，不再把内容停在输入框；多行面板（`/my ?`、`/auto` 状态、`/shellfix doctor`）仍用 DialogAlert 弹窗。

### Q：输入框区域出现红字（如 `[ShellFix][CodeMap] ... mode=built`）？

v2.3.3 已修复。根因：插件 `console.error` 直写进程 stderr，与 TUI 共用同一终端，原始文本覆盖渲染区，看起来像输入框里的红字乱码。

现在插件运行期**零 stdout/stderr 输出**，诊断信息统一写入：

```
~/.local/share/opencode/log/shellfix.log
```

（超过 5MB 自动保留最后 1MB；写入失败静默，不影响插件功能）

## 卸载

删除插件文件后重启 OpenCode 即可：

```bash
# 全局安装的
rm ~/.config/opencode/plugins/shell-fix.ts

# 项目安装的
rm .opencode/plugins/shell-fix.ts

# TUI 调度器（如已部署）
rm ~/.config/opencode/tui-plugins/shell-fix-tui.ts
# 并从 ~/.config/opencode/tui.json 的 plugin 数组中移除 "./tui-plugins/shell-fix-tui.ts"
```

## 开发与调试

### 本地修改

插件是纯 TypeScript 文件，修改后保存即可生效（重启 OpenCode 或重新加载插件）。

### 测试方法

使用 `shell-env-test.ts` 测试脚本验证 `shell.env` 环境注入：

```typescript
// test/shell-env-test.ts
const plugin = await import("../src/shell-fix");
const instance = await plugin.ShellFixPlugin({} as any);
const output = { env: {} } as any;
await instance["shell.env"]!({ cwd: "/test" } as any, output);
console.log("Env vars:", Object.keys(output.env).length);
console.assert(output.env.CI === "true", "CI should be true");
```

### 日志调试

v2.3.3 起插件**不使用 `console.*`**（会直写终端污染 TUI 输入框），统一用 `logLine(tag, ...)`：

```typescript
import { logLine } from "./lib/log-file";

"tool.execute.before": async (input, output) => {
  logLine("core", `intercepting ${input.tool} command`);
  // ...
  logLine("core", `converted: ${output.args.command}`);
}
```

日志写入 `~/.local/share/opencode/log/shellfix.log`（与 opencode 日志同目录；>5MB 保留最后 1MB）。`log` 开关关闭时，信息类日志不再写入（错误类仍写）。
